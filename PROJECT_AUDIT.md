# 1. Executive Summary

The current project is an academic desktop-based **Travel & Tourism Management System** built with **Java Swing (AWT/Swing)**, **raw JDBC**, and **MySQL**. It was designed as a single-user desktop client where all UI rendering, business logic, data validation, and database operations reside inside GUI screen classes.

### How the Current System Works:
1. **Launch Sequence:** The application initiates from [SplashFrame.java](file:///c:/Users/khushi/OneDrive/Desktop/codealpha%20interniship/TravelManagementSystem/Travel-And-Tourism-Hub/src%20code-travel%20&%20tourism%20hub/travel/management/system/SplashFrame.java), which animates an image frame using a multithreaded loop for 5 seconds before opening the [Login.java](file:///c:/Users/khushi/OneDrive/Desktop/codealpha%20interniship/TravelManagementSystem/Travel-And-Tourism-Hub/src%20code-travel%20&%20tourism%20hub/travel/management/system/Login.java) window.
2. **Session & Navigation:** Upon successful login, the application launches [LoadingFrame.java](file:///c:/Users/khushi/OneDrive/Desktop/codealpha%20interniship/TravelManagementSystem/Travel-And-Tourism-Hub/src%20code-travel%20&%20tourism%20hub/travel/management/system/LoadingFrame.java), which increments a `JProgressBar` on a background thread and then opens [Dashboard.java](file:///c:/Users/khushi/OneDrive/Desktop/codealpha%20interniship/TravelManagementSystem/Travel-And-Tourism-Hub/src%20code-travel%20&%20tourism%20hub/travel/management/system/Dashboard.java).
3. **State Management:** User state consists solely of a plain string `username` passed between class constructors (`new Dashboard(username)`, `new BookHotel(username)`, etc.).
4. **Architectural Style:** Non-layered, direct two-tier client-server architecture. There is no separation into Controller, Service, Repository, or Data Transfer Object (DTO) layers. Event handlers directly construct and execute raw SQL statements against a local MySQL database.
5. **Major Shortcomings:** 
   - Severe security risks (SQL injection across all forms, plaintext passwords, no session security).
   - Incomplete and simulated features (payments merely open external web pages in the OS default browser; destinations and hotels are static image slideshows; packages are hardcoded in Java arrays with zero database backing).
   - Desktop lock-in (`Runtime.getRuntime().exec` for Windows Calculator and Notepad; fixed-pixel coordinates breaking on high-DPI displays).

The target project **TravelSphere** will transform this legacy desktop codebase into an enterprise-grade full-stack web platform using **React + Vite + Tailwind CSS** on the frontend, **Spring Boot + Spring Data JPA + Spring Security (JWT)** on the backend, and an enterprise **MySQL** relational database, enhanced with **Google Places/Maps**, **OpenWeather**, **OpenAI**, and **Razorpay**.

### Schema Deficiencies:
1. **Zero Primary Keys:** Not a single table declares a `PRIMARY KEY`. Multiple identical records or duplicate usernames can be inserted without database-level rejection.
2. **Zero Foreign Keys:** There are no `FOREIGN KEY` constraints. Referential integrity is completely non-existent.
3. **Inappropriate Data Types:** Numerical monetary values (`costperperson`, `acroom`, `foodincluded`, `price`) and counts (`person`, `days`, `persons`) are stored as `varchar(...)`.
4. **Denormalization & Redundancy:** Customer identification type (`id`), document number (`number`), and phone number (`phone`) are duplicated into both `bookpackage` and `bookhotel`.
5. **Missing Tables:** There is no table for `destinations`, no table for `packages`, no table for `payments`, and no table for `reviews`.

# 7. Authentication Analysis

### 1. Registration (`Signup.java`)
- User inputs: `username`, `name`, `password`, `security` (dropdown), and `answer`.
- Execution: Directly concatenates values into an SQL insert statement:
  ```java
  String query = "insert into account values('" + username + "', '" + name + "', '" + password + "', '" + question + "', '" + answer + "')";
  c.s.executeUpdate(query);
  ```
- **Flaws:**
  - Password stored in raw plaintext.
  - No validation: spaces, empty strings, and special characters are accepted.
  - No uniqueness check: multiple accounts can register with the identical username.

### 2. Login (`Login.java`)
- User inputs: `username` and `password`.
- Execution:
  ```java
  String query = "select * from account where username = '" + username + "' AND password = '" + passcode + "'";
  ResultSet rs = c.s.executeQuery(query);
  ```
- **Flaws:**
  - `tfpassword` is a `JTextField`, so typed passwords are fully visible on screen.
  - Direct SQL injection vulnerability: inputting `' OR '1'='1` in both fields bypasses authentication completely.
  - No account lockout, brute-force protection, rate limiting, or session tokens.

### 3. Password Recovery (`ForgetPassword.java`)
- **Step 1:** User types username and clicks "Search". Query executes:
  ```java
  String query = "SELECT * FROM account WHERE username = '" + tfusername.getText() + "'";
  ```
  Populates the user's name and security question in cleartext.
- **Step 2:** User types an answer and clicks "Retrieve". Query executes:
  ```java
  String query = "SELECT * FROM account WHERE answer ='" + tfanswer.getText() + "' AND username='" + tfusername.getText() + "'";
  ```
  Directly copies `rs.getString("password")` into the `tfpassword` text box on screen.
- **Flaws:**
  - Exposes any user's security question and full name to any anonymous attacker.
  - Directly displays the plaintext password on screen rather than issuing a secure reset token.

# 8. Booking Analysis

### Hotel Booking (`BookHotel.java`, `CheckHotels.java`, `ViewBookedHotel.java`)
1. **Catalog Exploration:** [CheckHotels.java](file:///c:/Users/khushi/OneDrive/Desktop/codealpha%20interniship/TravelManagementSystem/Travel-And-Tourism-Hub/src%20code-travel%20&%20tourism%20hub/travel/management/system/CheckHotels.java) does not query the `hotel` table. It merely runs a 10-iteration loop loading images `icons/hotel1.jpg` to `hotel10.jpg` with a caption array.
2. **Hotel Selection Disconnect:** In [BookHotel.java](file:///c:/Users/khushi/OneDrive/Desktop/codealpha%20interniship/TravelManagementSystem/Travel-And-Tourism-Hub/src%20code-travel%20&%20tourism%20hub/travel/management/system/BookHotel.java#L58-L62), three extra hotels are manually added to the dropdown: `"The Taj Palace"`, `"Leela Ambience"`, and `"Holiday Inn"`. Because these hotels are not in the `hotel` table, selecting them and clicking "Check Price" returns an empty `ResultSet` and fails silently.
3. **Calculation Logic:**
   $$\text{Total} = (\text{costperperson} + \text{ac} + \text{food}) \times \text{persons} \times \text{days}$$
   where $\text{ac}$ is `acroom` if selected, and $\text{food}$ is `foodincluded` if selected.
4. **Data Integrity Failure:** If the user clicks "Book Hotel" without first clicking "Check Price", the booking is written with `price = ""` (empty string).
5. **Single-Record Limitation:** [ViewBookedHotel.java](file:///c:/Users/khushi/OneDrive/Desktop/codealpha%20interniship/TravelManagementSystem/Travel-And-Tourism-Hub/src%20code-travel%20&%20tourism%20hub/travel/management/system/ViewBookedHotel.java#L149) uses `if (rs.next())`, meaning if a user books multiple hotels over time, only the oldest/first record can ever be viewed.

# 15. Migration Strategy

The transformation to **TravelSphere** will follow a phased, decoupled approach that does not blindly copy flawed patterns:

```
[Legacy Desktop System]
  • Java Swing UI
  • Embedded raw SQL
  • No API layer
  • Unnormalized DB
         │
         │ (Extract Domain Concepts, Business Logic, and Seed Data)
         ▼
[Step 1: Normalized Database]
  • 3NF Schema with PKs, FKs, UUIDs, Timestamps, Enums
         │
         ▼
[Step 2: Spring Boot REST API]
  • Spring Security + JWT Auth
  • Spring Data JPA + Hibernate
  • Services for Hotels, Packages, Bookings, Payments
  • External Service Adapters (Weather, Places, AI, Razorpay)
         │
         ▼
[Step 3: React SPA Frontend]
  • Vite + Tailwind CSS + Lucide Icons
  • React Router for smooth navigation
  • Axios HTTP client with JWT interceptors
  • State management & responsive design
         │
         ▼
[Step 4: AI & Value-Add Enhancements]
  • AI Travel Assistant & Itinerary Generator
  • Admin Dashboard with analytics
```

### Guiding Migration Principles:
1. **Never port SQL string concatenation:** Every query must use JPA repository methods or typed criteria.
2. **Never store plaintext secrets:** Passwords must be hashed using BCrypt before database persistence.
3. **Decouple Frontend and Backend:** Communication happens exclusively over standardized JSON REST APIs.
4. **Normalize the Relational Schema:** Enforce strict primary keys, foreign keys, constraints, and audit timestamps.
5. **Mobile-First Responsive Design:** The new UI will look stunning on mobile, tablet, and desktop viewports.

# 18. Risks and Considerations

1. **Security & Data Privacy:**
   - Plaintext passwords in existing database require forced password resets or re-hashing during migration.
   - User document numbers (Aadhar/Passport) represent PII and must be encrypted at rest.
2. **External API Costs & Rate Limits:**
   - Google Maps and OpenAI APIs incur usage costs. Caching strategies (Redis or Spring Cache for weather and place details) must be implemented.
3. **Database Migration Strategy:**
   - Legacy data contains non-numeric strings in price columns (e.g., `"Rs 30000"`). A migration script with data cleaning is essential to avoid migration errors.
4. **Payment Verification Reliability:**
   - Reliance on frontend checkout completion is insecure; the backend must independently verify Razorpay webhook signatures before marking bookings as `PAID`.
5. **Browser Compatibility & Responsiveness:**
   - The application must support modern evergreen browsers and responsive breakpoints from mobile (375px) to desktop (1920px).
